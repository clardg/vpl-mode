# Project takeover

A VPL takes over from the product designer. Goal: no gaps between what the designer knows and what the VPL inherits. Source: Guru, VPL Handbook, "Project Handover".

1. **Access.** Confirm read access to the Figma file. Confirm edit access to the main file if the VPL will add missing screens and secondary flows (the product designer grants it). Confirm Coda roadmap access (the PM grants it). Draft a request for anything missing.
2. **Brief.** Run `project-brief` so the context file exists. Add `phase:` and the people who approve what.
3. **Understand the app.** Go through the Figma file for how the app works, not only the flows. Read the roadmap. Note how components, variables, and pages are set up, and how the file differs from the baseplate.
4. **Audit.** Run `vpl-design-audit` ([design-audit/SKILL.md](../../vpl-design-audit/SKILL.md)). Its open questions feed the call.
5. **Prepare the call.** Draft the invite message to the designer, and write questions specific to this project under these headings:
   - How the designer likes to work and what they expect
   - How the Figma components are set up
   - The app idea and the reasoning behind the design
   - Anything pre-agreed with the client on design or UX
   - The client's design preferences
   Drop any question the file or calls already answer.
6. **Team calls.** If the VPL isn't invited to project meetings, draft a note to the PM asking to join.
7. **After the call.** Pull the recording from Fathom if there is one, or ask the VPL for notes. Write answers to the context file under `## Takeover`, and move resolved items out of the audit's open questions.

**Done when:** the context file has the phase, approvers, file map, client preferences, pre-agreed items, and a list of gaps.

**Reply:** link to the context file, access still missing, the top gaps, and the call questions ready to paste.
